I would like to rethink if the current `LaTeX-codespace-template` needs restructuring. The reason is the following: as the number of projects in which I am involved grows, so does the number of repositories hosting the projects; however, most of those projects are primarily about a *single* manuscript (research paper, monograph, textbook, survey, etc.) written in LaTeX. Many of my papers joint with Iovino and our students at UTSA are currently hosted in one-off repositories *not* derived from the template nor following its conventions. Each such repositories have various additional files (e.g., BibTeX, figures, possibly some scripts), but usually have the goal of producing a *single* document. Since Iovino, our students and I have written and continue to work on new manuscripts, the number of individual repositories grows, BibTeX files diverge (worse: some reference lists are *inlined* at the end of the LaTeX source and not BibTeX-generated), stylistic and file-formatting conventions diverge or simply go against sane and sustainable practices, etc.

I would like for the template to be redesigned so as to accommodate multiple sub-projects coexisting in subdirectories of the root. The idea is to treat each such *subdirectory* as the working space for the respective paper in basically the same manner that we are using the dedicated *repository* for the paper right now. In that way, many papers will be consolidated in the same repository, which provides shared infrastructure and helps organize the work.

The template must be easy to use for users having limited familiarity with Git/GitHub. In particular, it cannot use submodules, but rely on well-thought vendoring of shared BibTeX and macro/style files `.sty`. It is critical to have a proper configuration for `latexmk`; I think that is usually done via a hidden file `.latexmkrc`, but if it can be done with a non-hidden file, I find that preferable. I also want for the usual/manual "pdflatex + bibtex + pdflatex" workflow to still "just work" (even if the temp/aux files don't go in the root in that case). This may require putting symlinks to vendored files alongside the TeX source: it's okay to do so (to accommodate users who follow obsolete workflows).

One important consideration: The repository should impose VS Code configuration and add-ons necessary to work in those projects. As an example, Iovino had a lot of frustration because he didn't know how to automatically soft-wrap long lines in TeX files. Such soft-wrapping is a mandatory default; certainly, when it comes to TeX files. Apart from that, true persona-preference settings such as choice of theme and customized keybindings should *not* be part of the VS Code configuration per the template.

Another important consideration: The instructions for agents `CLAUDE.md` and for humans in `README.md` should clearly explain how to work with multiple sub-projects within the same repository. This includes specifying the expected directory structure, how to compile individual papers, and how to manage shared resources such as BibTeX and style files.
